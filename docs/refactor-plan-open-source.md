# 开源框架迁移重构方案（refactor-plan-open-source）

> 依据：用户指令（2026-10-27）——**量化交易核心必须使用成熟开源框架，
> 零自研**；"给 AI 提供数据和参考策略"的部分不属于量化系统，可保留。
> 本方案为决策文档：**用户拍板后才动代码**；执行进度回写
> `docs/founding-mandate.md` §5。

## 1. 分层架构（2026-10-27 用户修正版，取代原"零自研"表述）

> 用户定调：「零自研不现实，不然没法开发。把计算、市场等复杂的部分交给
> 社区成熟框架，有了量化框架后把我们本来想要实现的功能盖上去；同时理性
> 审视社区部分；不能再有 AI 随意下单还通过的事情发生。」
> 原"零自研"红线**撤回**，改为下列三层：

### L1 量化核心层（计算/市场语义）—— 社区框架，不自研
撮合/账本/T+1/涨跌停/费用/滑点/回测/风控**判定**。框架缺口的 A股合规判定
优先用框架扩展点，实在没有才登记为「自研保留件」并配 parity 门禁。
**可判定红线**（采纳员工 P2-7）：任何影响成交价、持仓、盈亏、下单/拒绝
结论的**数值**，必须来自框架 API 返回值。

### L2 功能层（我们本来要实现的产品功能）—— 自研，盖在框架之上
AI 决策链（上下文/决策/审计）、数据供给（akshare/母库适配器）、面板/CLI/
op_log、cron 运维、**安全门禁**（尺度闸/执行价偏离闸/条件单闸/止损门禁/
配置接线回归——门禁消费框架 API 的数值做 fail-closed 校验，本身不计价）。
这一层的自研是产品本身，合理且必须。

### L3 审查层（防走歪）—— 双同事审查制
同事 A（Qoder）：选型/spike/对我方案的反驳审查；同事 B（Hermes）：
现网 correctness 独立审查（H 系列）。**我的代码与决策推送后须经至少一位
同事复核**；配套：parity 门禁、事故回归门禁、NaN 非有限值门禁。

## 3. 推荐架构：双框架

```
┌─────────────────── 保留自研（量化系统外） ───────────────────┐
│ akshare/SQLite/母库 ──► 数据适配器 ──┐    AI 决策链(LLM/审计) │
│ 面板/CLI/op_log ◄── 状态订阅 ◄───┤    └──动作/条件翻译器──┤
└──────────────────────────────────┼───────────────────── ┘
                                   ▼
 ┌── rqalpha 6.x（回测线）──┐   ┌── vnpy 4.x（交易线，常驻）──┐
 │ 策略回放/成交/费用/资金曲线   │   │ EventEngine + MatchingEngine  │
 │ optimize/walkforward 由胶水  │   │ 账户(T+1 冻结)/风控/条件单    │
 │ 调度，判定全在 rqalpha 内     │◄──┤ AI/规则下单走 vnpy Order API  │
 └────────────────────────┘   └──────────────────────────┘
```

- **回测线 → rqalpha**：接管 `engine/backtest.py`/`optimize.py` 的**判定**；
  我们的 walkforward 调度、回测指纹（`provenance.py`）保留为胶水/审计。
- **交易线 → vnpy**：接管 `PaperBroker`/`RiskManager`/`runner`/`ConditionRunner`
  的**判定与成交路径**；AI/引擎/面板全部改经 vnpy 下单 API 与账户查询。
- **Python 统一 3.13**：本地建 3.13 venv（3.14 下 vnpy 只能装到 4.0.0），Pi 已是 3.13.5。

## 6. 风险清单

1. **Python 版本**：vnpy 4.1+ 未覆盖 3.14 → 全线统一 3.13（Pi 已满足）。
2. **Pi arm64 + 无 GUI**：vnpy 主包拖 PySide6/TA-Lib；M0 验证 `--no-deps`
   最小依赖安装（loguru/pyzmq 等纯 Python 核心）——**最大技术不确定性**。
3. **rqalpha 非商业条款**：个人本地研究使用符合条款；若未来商业化需
   RiceQuant 授权或换 backtrader（M1 parity 框架已抽象，替换成本可控）。
4. **数据适配**：rqalpha 需要 bundle 风格数据 → akshare/SQLite 适配器（胶水）。
5. **认知/运维成本**：双框架学习与升级跟踪；由 T5 反驳审查+文档缓解。
6. **性能**：vnpy 事件驱动在 Pi 每分钟 tick 负载下无压力（轻量级）；观察期验证。
7. **vnpy 4.x wheel 瘦身**（M0 已证实）：2.x 的 `app/` 层不在 wheel 内；
   **常驻模拟撮合网关的载体待定**（M0b 定论，阻塞 M2 设计不阻塞 M1）；
   撮合实现已确认在 `vnpy.alpha.strategy.backtesting`。

### 7.1 决策

**主线：rqalpha 6.4.2 单引擎（回测 + 本地模拟撮合 + A股口径）**，
并行给 **akquant 一个半天的"挑战者 spike"**（两个否决性问题，见 7.2），
**hikyuu 出局**（3.0 无 Windows wheel，开发机需自编译 C++，双平台一致性代价过高）。

### 7.2 推理（为什么是这个结构）

1. **硬门槛排序**：本项目的不可妥协项是 ①A股口径（T+1/涨跌停/费用/整手）
   ②回测与模拟撮合**同一引擎**（路线图纪律 3）③Pi arm64 + Windows 双平台可装
   ④活跃维护。现有证据下**只有 rqalpha 全部已实证**：
   - 员工 Windows 端到端跑通（bundle 3.3GB、回测返回 summary）；
   - 我的 Pi arm64 spike：装好、导入成功、MainEngine 级别无问题（rqalpha 侧）；
   - A股语义源码取证最全（2023 印花税日期/涨跌停/模拟撮合器/T+1 账户）。
2. **但 akquant 是唯一可能翻盘的挑战者**：MIT 许可（永久消除合规张力）+
   与 akshare 同门（数据适配天然）+ Rust 内核 + 高频维护。它输在哪没验证过
   （模拟撮合能力、aarch64 轮子）——**用半天、两个否决性问题验证，
   比全量三选一打分便宜且同样有效**。通过 → 终选改 akquant；不通过 → rqalpha 定案。
3. **为什么不再漫无目的打分**：其余维度（许可已接受、bundle 已留、NaN 门禁
   已列入 M1 条款）不再是决策变量；决策树只剩一根分叉，测那根分叉即可。
4. **Python 版本**：rqalpha 在 3.14（开发机）与 3.13（Pi）**双端实测可装**，
   **不降级**——原 §7-C"全线 3.13"随 vnpy 冻结一并作废（员工 P1-3 正确）。
5. **账本历史**：原则维持"归档 + 切换日新开账"（§4），随终选框架在 M2 重确认。

## 5.1 M1 验收门禁（采纳员工 `report-defect-attribution.md` §6，2026-10-27）
